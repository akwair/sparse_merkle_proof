## 判断

**有条件值得先做。** 主代理最新收窄后的方案比再次扩大 JSON/bitmap 对照更有价值：同一 Celestia 原生宿主、同根的合法 distinct queries、固定验证工作，控制批量和真实哈希路径聚类；独立分析原生省略、批内共享、压缩器对象生命周期三个不同机制。其目标应是得到可以复核的条件取舍，不是寻找一个必须获胜的新编码。

## 必须锁定的同任务边界

### 1. 合法输入与“聚类”的定义

冻结上游 `treehasher.go` 的 `path(key)` 调用散列。当前 SHA-256 配置下，原始 key 的字节前缀或数值相邻不代表树路径相近。聚类必须按**实际 SHA256(key)** 选择已有树中的查询，不能改 hash、直接构造路径、补齐原生路径或插入伪节点。定位：[本地冻结源码](WORKSPACE/study/crypto_study/round3_qpc/external/smt/treehasher.go:30)；固定版本 `dba215ccb88452c31d823bf156d8f35406c1dc04`。

这里的 key 指传给树 API 的实际 key 字节。现有外层生成器已经先把标签散列成 key，因此不能误把生成器的第一次散列当成最终路径；应再次按树实际执行的 `SHA256(key)` 分类。

建议主矩阵只用 membership，先回答清楚一个问题；若主代理决定同时保留 non-membership，应作为独立层，不与 membership 汇成一种“平均证明”。后者可能含 `NonMembershipLeafData`，其长度与见证类型必须保留。不要为增加场景数而掩盖语义差异。

对同一 domain/N 的一棵冻结树，均匀和聚类策略都从相同合法键集合选查询。每个 bundle 内无重复，所有模式处理完全相同的 root、顺序、keys、values 和 proof 字段。固定 key/value 长度；不要让聚类组的 value 使用重复文本而均匀组使用随机字节。

两处特别注意：

- **q=1 没有跨查询共享。** 可作为共用单查询基线，或作为聚类选择的负控制；不可把单查询分组差别解释为批内聚类效应。若两个策略的单查询样本不同，应说明只反映位置/路径差别。
- N=4096、最高4bit同前缀的某个桶，不一定有足够键供 3×128 个跨 bundle 不重复查询。若要求跨 bundle 不重叠，预先轮换前缀或指定容量合格桶的确定性选择；若允许跨 bundle 重叠，则记录重叠。容量不足应按冻结规则处理，不能看时间结果后重抽树。域和 bundle 是有限固定输入，不是独立种子总体。

抽样政策改变也可能改变原生 depth、占位节点数和非占位节点数。应记录这些分布，避免把全部时间差都归因于“共享”。若要声称共享是独立因果因素，需要额外的匹配或干预证据；当前矩阵只足以估计所定义抽样政策的条件差异。

### 2. 压缩单位与生命周期

“Independent zlib”必须写清是**每个 bundle 一个独立 stream**，还是每份 proof 一个 stream。候选字典跨同一 bundle 共享节点时，强基线必须允许 zlib 看到同一完整 bundle；只比较逐 proof 重置的 zlib，会偏置共享机会。Round3 已有 whole-bundle zlib-ordinary / zlib-compact，可作为对照起点。

Fresh writer 和 Reset writer 是**对象生命周期的对照**。每个 bundle 都结束一个完整 stream；Reset 不得带入上一消息历史，不能把跨消息预热字典免费提供给某个模式。官方 Go 文档说明 Reset 恢复 writer 初始状态：[compress/zlib.Writer.Reset](https://pkg.go.dev/compress/zlib#Writer.Reset)。在冻结版本、同 level、同输入和同写入序列下，测试其帧字节一致；该测试不意味着 Go 承诺跨版本输出逐字节不变。

主分析应分别比较：

1. ordinary 与 compact：既有默认节点省略的效果。
2. 同一种完整表示的未压缩与 whole-bundle zlib：压缩的增量效果。
3. 同帧 zlib fresh 与 Reset：生命周期的效果，字节必须相同。
4. 一个固定字典封装与其明示父格式：节点共享的增量效果，同时与 best observed whole-bundle zlib 选项比较 Pareto 位置。

不能把四种机制的最佳组合差异统称为“字典算法加速”。若字典只加在 ordinary 或只加在 compact 上，必须明确父格式，不要同时换 mask、计数字段、根存储次数等公共部分。

Reset 的构造成本若发生在计时外，其结论是**已初始化对象的稳态处理**；应同时保留 fresh 结果，报告生命周期边界。不要把它称为冷启动成本。全部计时路径包含必要的 Close、解压校验、字段解析与原 verifier。字典建表、索引编码、解码恢复与资源检查均在候选自身计时内；不可提前缓存候选输出。

### 3. 可选字典只承担明确的控制作用

可选择一个简单、每 bundle 自包含的 hash 表封装：字典中存原32-byte节点值，原位置存有界索引，重建原顺序 SideNodes 后调用原 verifier。它是已知去重机制的控制，不能声称新密码算法。与 zlib 的 preset byte dictionary 或跨消息缓存是不同设计，不要混称“字典”。

需在实施前写清：字典涵盖哪些字段，是否包含默认节点，排序或首次出现规则，索引宽度/规范编码，重复字典项与未引用项是否允许，以及完整展开预算。保留 root/key/value、非成员见证、query 次序和数量。验证时仍对每条 query 调用同样的普通 verifier，不得只在候选中跳过已验证的 query。

独立重建应检查完整对象相等和原始普通帧的确定性重编码；不能仅凭“最后都 Verify=true”判断等价。负例至少覆盖错误索引、越界计数、未消费尾部、错误根/值/见证、重复或不规范表示以及超预算展开。若任何模式依赖外部可信 root/预期查询，所有模式都应使用同一个预期值，不能以帧内自报 root 取代信任锚。

## 最低有价值的论证包

以下是值得形成投稿稿件的证据底线，不是形式上的录用充分条件。

**A. 一条实际决策与三条可回答问题。** 对象是已有逐证明 verifier 的实现者，决定给定同根查询 bundle 使用哪种完整表示。RQ1：原生 compact 在哪些占位节点数/深度下增大或缩小？RQ2：distinct 查询的批量与路径聚类是否改变跨证明共享和可选表示？RQ3：压缩生命周期能否改变本地时间排序，而不改变帧字节？局部时间/字节取舍不是网络时延预测。

**B. 强且同机会的对照。** 固定普通二进制帧；原生 compact；whole-bundle 通用压缩；同帧 fresh/Reset；至多一个已知字典控制。所有模式获得同一输入与批次边界，公共元数据取消方式一致。不能只有人为较弱基线。

**C. 字节账本先于故事。** 每个 bundle 记录查询数、原生 side-node 总出现次数、占位节点数、非默认节点总数/unique 数、完整 proof 的 unique 数、字典字节、索引字节、mask/length/envelope 字节。当前 compact 的精确恒等式应继续逐帧核对。若字典将 T 次32-byte节点出现改成 U 个唯一节点及 T 个 w-byte索引，且其净额外元数据为 H，则该结构的净节省是 `32(T-U)-wT-H`；实际格式若不同，重新按字段核算，不能套错式。它是账本，不是密码定理。

**D. 时间证据不借字节推断。** 在同 bundle/同 repeat 内配对；同时报告编码、解码/恢复、验证以及总路径。QPC 测到的是本地墙钟处理时间，若未测线程/进程 CPU time，文中不能把它称为精确 CPU 时间或周期成本。报告绝对量级与计时器开销相对尺度；不因某组不显著而继续追加重复直到胜出。

**E. 条件规则需要超出同表择优。** 最低要求是在事先冻结的 domain/输入划分上检查结构解释是否继续成立。可以报告观测到的 Pareto 集合和预算可行条件；不能把每个 cell 事后选最快模式称为在线自适应方法。若提出由结构计数选模式的规则，规则需先冻结，再评估未用于挑规则的固定输入；实际选取/计算这些计数的开销不能从在线成本中漏掉。

**F. 有限外推要具体。** 主张限定为该 pinned library、Go 实现、两种 N、这些查询政策和本机；不排全 SMT 名次，不推导真实网络/并发提升。两域仍用 seed 3407，可以有互不重叠的确定性域标签，但不是两个独立随机种子。正式数据应保留所有长尾、失败、零时长检测、对象生命周期和原始帧。两篇参照论文的统计不足不构成降低本实验规范的理由。

## 主要反例与可重复性风险

| 风险/反例 | 对论证的影响 | 最小应对 |
|---|---|---|
| q=1 或几乎没有共享节点 | 字典元数据必然容易亏损 | 保留为预期负控制；不要删除 |
| compact 已无默认节点可省 | compact 扫描/恢复增加工作，而 mask 增大 | 用原生结构逐帧解释；不是发现新密码缺陷 |
| distinct 查询也共享大量上层 siblings | 均匀与聚类可能都高度可压缩，差别很小 | 记录真实共享率；允许“聚类政策不决定选择”的结论 |
| 聚类减少/增加 path depth 等 | 时间变化不唯一来自共享 | 记录 depth/placeholder；收缩因果措辞 |
| bundle 顺序改变 zlib 而不改变独特节点数 | 仅用共享率无法预测通用压缩 | 同一 query multiset 的顺序作为预定稳健性检查；固定规则而非找最佳排序 |
| zlib 已利用批内共享 | 简单字典可能全被支配 | 单列 Pareto；不能只对比逐 proof zlib |
| Reset 变快来自分配/初始化摊销 | 不能据此宣称新的共享算法 | 同字节生命周期对照；不把原因细化到GC/缓存，除非另有证据 |
| 验证成本占总路径大部分 | 编码明显变快而总时间不变 | 总时间仍为主结果，局部改进单列 |
| 字典扩大驻留/展开内存 | 相同字节和更低时间未必全面更优 | 最低给字典/展开预算；没有测量就不主张内存优势 |
| 相同集合反复计时和缓存预热 | technical reps 不代表输入总体 | 以输入为单位呈现，再显示配对波动；避免所有时序行池化成独立样本 |
| synthetic hash-prefix selection 不对应常见应用查询 | 可以测结构机制，不能声称真实热点业务收益 | 正确命名为路径聚类合成控制；不冒充业务 trace |

DEFLATE 的回看距离有 32768 bytes 上限，因此同样的重复总数并不保证同样的压缩结果；字节距离/排列可能重要。[RFC 1951 §3.2.5, p.11](https://www.rfc-editor.org/rfc/rfc1951) 此处只是标准机制说明，不是对尚未测得现象的原因归属。zlib preset dictionary 另见 [RFC 1950 §2.2/§8.1](https://www.rfc-editor.org/rfc/rfc1950)，不应与本候选的自包含节点表混为一物。

## 哪些结果仍值得报告，哪些应止损

### 有价值的结果不要求字典胜出

- 找到可重现的条件反转：例如小批次 ordinary 在本地处理上占优，增加批量后某种表示的节省可由共享/元数据账本解释；还需完整报额外时间，不能只取体积。
- compact 在原生短路径上仍很少获益，而 batch 压缩能利用另一种冗余；这可以把“单证明省略”和“跨证明共享”区分成读者可用的认识，前提是相对既有研究的增量被讲清楚。
- Reset 在不改变帧字节的情况下改变了与其他模式的本地时间排序。这将直接限定 Round3 的 fresh-compressor 成本结论，属于有价值的实现经验；仅测出预期的初始化减少仍未必足以单独成为一篇论文。
- 字典被 whole-bundle zlib 一直支配，但结构账本能解释为什么，且负结果在未用于选条件的输入中保持。它可以成为完整实证论文的一部分，不能单凭“候选失败”包装突破。
- 字节明显减少、总处理时间不改善，也值得原样报告。可给 local bytes/time Pareto 图；不自行填入网络带宽把它改写成已验证网络收益。

### 应停止该候选作为主论文升级的情形

1. 新矩阵只是重演“重复越多越容易压缩”或“去重有索引开销”，没有纠正可指明的实际误判，没有额外决策条件，且最近文献已经给出相同认识。应承认增量不足，不靠更多模式或计时行数补足。
2. 可选字典仅在重复同一 query 或不公平的逐 proof zlib 对照下胜出；主矩阵 distinct queries 与 whole-bundle 强基线下没有价值。可以删除字典主张，保留负证据；不要改题为新协议掩盖失败。
3. 观察到的模式排序由一个前缀桶、一个输入顺序或超小时间量级支配；有意义差异小于预先定义的测量/实践辨别范围。不要追逐噪声挑条件。无法形成稳定条件结论时止损。
4. 所谓收益依赖计时外建表、免费持久压缩历史、删掉普通模式必须验证的 query、改变根/证明关系，或省略公共字段。先修设计；若修后贡献消失，原收益不可发表为有效结果。
5. 必须声称“最优批证明/通信格式”才显得有价值，却又不能面对 multiproof、请求去重/缓存等相邻方案。应收缩为兼容封装成本研究；收缩后若无读者价值，换题而非堆模块。

**建议的下一步是先锁定上述边界，再做功能与少量可证伪检查，只有确认输入控制确实改变了要研究的结构量、强基线实现正确且题目仍有增量时，才制定正式 PLAN。** 正式阈值应来自要支持的使用决策与可辨别量级，不能机械搬用上一轮 70%/10% 或看到结果后制定。用户固定 seed=3407 保持不变。本审查未授权、启动或声称完成任何新的性能实验。

- H-locality 每域有 8 个预设比较：2 N × 2 kinds × q∈{32,128}。每侧是三个 bundle 的 dictionary/ordinary bytes ratio 中位数；development 要求每个差至少0.10，confirmation 每个只要求方向同样为 clustered 更低。
- H-lifecycle 每域有 48 个预设比较：3 zlib representations × 2 N × 2 kinds × 2 patterns × q∈{1,8}。development 全部 median paired reset/fresh total ratio≤0.90；confirmation 全部<1.00。q32/128 明确描述性扩展。
- 两域提前生成、相同固定 seed、正式测量后不得调参；不论 development 是否通过，confirmation 都执行。这与“先失败即不运行后续确认”的旧门控不同，但本轮已明确规定，逻辑不冲突。
- 三个 bundle 固定前缀0/5/10、q条件嵌套且允许记录重叠，解决了仅在一个前缀桶里强求384个不同 key 的容量问题。容量不足视为设计失败，不改前缀寻优。
- 整 bundle zlib、fresh decoder不复用、只复用 writer状态且逐帧 Reset，保留了明确的生命周期干预。q1 不作跨查询聚类结果。所有模式逐项原 verifier，禁止缓存验证。
- 字典恒等式 `30*S-32*U-2` 与“每次32-byte节点改为2-byte索引，唯一节点仍32 bytes，增加2-byte字典计数”的候选格式一致。实现还必须确认别的字段确实在差分中取消。

### registration 前应收紧的分析/表述定义

1. **local wall time 与 CPU time 名称。** 正式计划的 QPC 指标是本地墙钟处理时间。RQ3 和适配文档出现的 CPU 用词应统一收紧；若未来另外采集 CPU time，则需另定义测量方法和指标，不能混称。
2. **跨域 effective cell 的匹配键。** 建议明确为 `(N,kind,pattern,q,mode)`，分别取 development 与 confirmation，不能把 domain-specific cell 当成可直接自我确认的单位。
3. **非对称确认不能被省略。** RQ3 development bytes≤0.80，confirmation 只要求bytes<1且total ratio≤1.05。它不等于“两域都节省至少20%”。同样 H-locality 的10个百分点、H-lifecycle 的10%改善只由development门槛要求，confirmation验证方向；不能把总门控通过描述成两域都达到相同幅度。
4. **Pareto 的坐标/判定尚需明文固定。** 该版本只写完整 Pareto 比较，未明确聚合方式。一个可用选择是每domain/N/kind/pattern/q，以 `max3(mode/ordinary bytes)` 和 `median63(paired mode/ordinary total time)` 作坐标，按两项≤且至少一项严格<定义描述性支配。它不代表每个 bundle 或每个 request 都被支配。也可选其他明确规则，但不能见结果后选择。Pareto 的≤1与工程容忍门槛1.05不要混淆。

以上已通知主代理。没有发现需要停止实现的硬冲突；建议上述文字和分析定义在正式 source/config registration 前收口。正式实现审查另需检查帧恢复、资源上界、状态重置、旧codec逐字节兼容、计时对象存活、配对键和失败状态，当前尚未给出通过结论。
