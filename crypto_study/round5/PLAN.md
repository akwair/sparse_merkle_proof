# Preregistration: Round4 replication on a Linux CPU server

Date: 2026-10-23. Literature and placement decisions are recorded in LITERATURE.md and ADAPTATION.md. This plan is prospective for Round5 formal measurements. The Windows Round4 outcomes are already known and remain immutable. Functional tests and unmeasured equivalence checks may precede registration; formal timing may not. No formal run is authorized by writing this document alone.

## Objective and scope

Repeat the exact Round4 valid-fixture task on the available Linux CPU server and assess agreement of its original registered conclusions. Preserve all hypotheses, thresholds, matrices, one seed, warmups, repetitions, workload strings, codecs and verification semantics. Add no mechanism and make no prediction that the server will improve a gate. A disagreement is a valid result, not a reason to retune or replace either platform's data.

The comparison changes CPU, operating system, clock backend and execution environment together. It is a cross-platform replication, not an isolated CPU intervention. No pooled timing estimate, hardware-only causal claim, machine-population inference, network-speedup claim or universal-best-method claim is planned.

## Original gates, evaluated separately on each platform

**H-locality.** For each domain, N, kind and q in {32,128}, compare the median of the three dictionary/ordinary byte ratios in clustered and dispersed queries. Every development comparison must have a dispersed-minus-clustered difference >=0.10; every confirmation comparison must have a strictly positive difference. All exact size identities and restored proofs must pass. There are eight comparisons per domain. Equal cross-platform bytes imply the same byte-only decision; this is an invariance check, not an additional independent sample of a locality effect.

**H-lifecycle.** For each zlib representation (ordinary, compact, dictionary), N, kind, pattern and q in {1,8}, take the median of 63 matched reset/fresh total-time ratios (three bundles x 21 repeats). Every development comparison must be <=0.90; every confirmation comparison must be <1.00. Fresh and Reset frames must be identical. There are 48 comparisons per domain. q={32,128} remains descriptive only. Do not move a failed q=8 condition out of the gate or substitute a favorable subset.

**Conditional engineering gate.** For each domain-specific cell and mode versus ordinary, use the worst-of-three bundle byte ratio <=0.80 and the median of 63 paired total-time ratios <=1.05 for development. Match confirmation by (N,kind,pattern,q,mode): an effective result requires the development pass, confirmation worst byte ratio <1.00 and confirmation median time ratio <=1.05. Confirmation checks byte direction, not the development 20% magnitude. Report all mode/cell outcomes and all failures, without requiring one mode to win everywhere. These are descriptive engineering gates, not significance tests.

Preserve Round4's H-locality pass, H-lifecycle failure and zero effective alternatives. Round5 receives its own decisions using the same rules. Report gate-level and individual-comparison agreement/disagreement side by side; a new pass never retroactively changes a prior failure.

## Frozen matrix and order

- The only seed is 3407. Keep domain strings exactly `r4/dev/3407` and `r4/confirm/3407`; do not rename fixture strings to r5. Both domains execute regardless of development outcomes and neither can select a subsequent change.
- Celestia SMT commit `dba215ccb88452c31d823bf156d8f35406c1dc04`, SHA256, and all upstream update/prove/compact/decompact/verify functions remain unchanged. The Linux executable uses the same Go 1.27.3 release as the Windows baseline.
- N={4096,16384}. Keys are SHA256(`r4/{domain}/3407/key/{i}`); values use the corresponding `value/{i}` string. Absent candidates use `absent/{i}`, remain absent and distinct, and scan the fixed 65,536-candidate cap for every tree. Persist the complete four tree checkpoints. Within a domain, the smaller populated key/value set is a prefix of the larger one; the trees are not independent samples.
- q={1,8,32,128}; member/absent and dispersed/clustered conditions are separate; three bundles per cell. Each bundle has q distinct keys in fixed order. Batch prefix nibbles are {0,5,10}; clustered queries satisfy upper4bits(SHA256(key))=prefix. Dispersed candidates retain Round4's deterministic hash-rank order. q conditions are nested prefixes; cross-bundle and cross-q reuse is retained. Candidate insufficiency is a design failure, not permission to choose a new prefix or seed.
- Nine timed modes, in the original base order: ordinary, compact, dictionary, zlib-ordinary, zlib-compact, zlib-dictionary, reset-zlib-ordinary, reset-zlib-compact, reset-zlib-dictionary. The default remains ordinary. Zlib compresses the entire bundle payload at level 6 with no external dictionary. Reset clears history before each frame, retains a writer per representation across the whole run, and uses the same fresh buffers and fresh decoders as before.
- Total per platform: 64 domain-specific cells, 192 bundles, 9 modes, 21 repetitions = 36,288 timed observations. Two warmups per mode per bundle. Three Reset modes duplicate their fresh formats, leaving six unique frames per bundle and 1,152 archived frames.
- A single pseudorandom generator seeded 3407 first shuffles all 192 bundles, then its continuing draws permute mode order in each paired repetition. Keep the original generator and draw sequence. Match both bundle order and every (bundle,repeat,mode,order) tuple to Round4. Preparation/checking must not advance this generator. Development and confirmation are interleaved in the same process, not independent runs or independent seeds.

## Platform and timing contract

The target inventory in `prior/cloud_environment.json` records Ubuntu 22.04.4 LTS, Linux 6.5.0-44-generic x86_64, Intel Xeon w5-3425, 12 physical cores/24 logical CPUs and about 125.26 GiB total RAM. The Windows baseline was an Intel Core i5-11300H with four physical cores/eight logical CPUs, about 15.79 GiB RAM and Windows 11. Exact archived environment records take precedence over these rounded descriptions.

Build on Windows using the existing hash-verified Go 1.27.3 toolchain, `GOOS=linux`, `GOARCH=amd64` and `CGO_ENABLED=0`. The build command is `go build -o conditional_runner .`. Freeze the executable hash and actual build provenance before formal launch. Preserve original archive metadata in dependencies.json. No server-side toolchain replacement or library upgrade is part of this protocol.

Set GOMAXPROCS=8 explicitly, matching Round4's recorded actual value. Leave GOGC and GOMEMLIMIT unset. Retain runtime defaults; do not change affinity, power, CPU frequency/governor or machine scheduling settings. Execute one sequential benchmark process. No study tests, compilation, rendering or analysis overlap formal timing. The shared server is not claimed to be isolated: save `resources_before.json` and `resources_after.json` with load averages, CPU visibility/affinity, relevant process/cgroup limits and available memory immediately around the runner. These observations provide context and are not criteria to drop observations or select a rerun.

Use `Go monotonic time.Since` against an unmodified monotonic epoch; timestamps are integer nanoseconds and `clock_frequency=1000000000` denotes units per second. The pinned Linux runtime source uses CLOCK_MONOTONIC. The functional timer tests must establish nondecreasing reads, resolvable short work and exact elapsed/stage arithmetic on the target; a numeric frequency alone is not evidence of actual resolution. The baseline keeps its original QPC 10,000,000 Hz measurements. Do not rewrite its timer or rescale it using the Linux convention.

The timed path stays encode -> decode -> ordinary verification of every query. Retain the same timestamp placement, error checks and KeepAlive placement. Include clock overhead without subtraction. Full restoration equality, reference-byte comparison, preparation/proof construction, writes and root acquisition/authentication are outside timing. Each observation requires positive total time, nonnegative stage times and encode+decode+verify=total exactly. Local elapsed time includes runtime and OS scheduling effects; it is not isolated CPU time.

## Analysis and descriptive platform comparison

Run the original analysis separately for each platform without numeric or threshold changes. Keep all samples. Per domain-specific cell/mode report bytes, within-platform paired mode/ordinary ratio, Reset/fresh ratio where applicable, per-stage medians, total median/p95/max, slower-pair and >1.05 counts, and every gate outcome. Percentiles use the original sorted-sample linear interpolation at `(n-1)*p`.

Keep the original summary Pareto rule: coordinates are (worst-of-three byte ratio, median-of-63 paired mode/ordinary time ratios). Another mode dominates only when both coordinates are no greater and at least one is strictly smaller. This is a cell summary, not per-request dominance; the engineering tolerance 1.05 is not part of Pareto dominance. Report fronts separately by platform.

The additional cross-platform summary in `CROSS_PLATFORM.json` first requires exact equality of 1,542 corpus artifacts: four tree checkpoints, 192 bundles, 1,152 unique frames, 192 per-bundle diagnostics, the combined diagnostics and execution-order file. All 36,288 observation identities must match in execution sequence, including domain,N,q,kind,pattern,batch,cell,id,repeat,order,mode and bytes. Repetition labels identify the same scheduled work but do not make observations on different platforms simultaneous timing pairs.

For all 576 domain-specific cell/mode combinations, report Linux median total time divided by Windows median total time, explicitly a **ratio of cell medians**. Each median contains the platform's original 63 observations. Also show each platform's original within-platform paired mode/ordinary ratio and its own median, p95 and maximum total time side by side. Do not replace this with a median of cross-platform per-repetition ratios, add unplanned tail ratios, pool raw times across platforms or calculate independent-sample confidence intervals over technical repeats. These are descriptive condition matches across two noncontemporaneous runs, not randomized hardware effects or independent machine replicates.

Compare H-locality and H-lifecycle overall decisions, their constituent comparisons, and effective-mode/cell pass/fail states. Report changed decisions and near-threshold values without changing inequalities or discarding slow samples. Record structural identity separately from timing agreement. No aggregate portability-success threshold is introduced. Results are interpretable for these observed environments even if every timing decision agrees, and even if no alternative passes again.

The original optional payload model remains `L(B)=t_local+8*W/B` using each bundle's 21 paired time differences and its own bytes. Keep all quadrants/equalities, p10/p90 differences and the original break-even calculation without fitting or selecting a bandwidth. Compute it separately for each platform only. It remains a sequential non-overlap illustration, excludes RTT/headers/queuing/sockets and has no gate or evidence of real network acceleration.

## Launch, retention and amendments

Formal launch uses GNU nohup and a unique new work directory. Standard output/error append to `../round3/ALL_RUNS.log`; no old directory or log is overwritten. The launcher must retain its dispatch record and actual process exit, while the run stores source/config/registration snapshots, before/after resources, runner exit, measurements, checkpoints, frames, evaluation, report and completion hashes. Dispatch success alone is not completion. Completion requires successful actual exits, complete expected counts, post-run hash checks and no failure record.

Do not remove outliers, truncate slow cells, stop early for poor performance, tune modes, change seeds, rerun until a favorable result, or reinterpret a failed strict inequality as a pass. Keep every failure, partial run and slow sample. Shared-load context does not authorize selective deletion or silent replacement. An interruption or correctness failure is documented; a later attempt uses a new work directory and records why it occurred. A code/protocol change after registration requires a dated amended registration and new work directory, preserving the old registration and failed data.

The second platform extends environment coverage while retaining the original weaknesses: synthetic input, one seed, nested/reused queries, one formal process per platform, shared-server variability and coupled OS/hardware differences. 本实验为单种子，存在随机噪声风险。Neither two deterministic domains nor technical repeats establish independent-seed or broad cross-machine robustness.
